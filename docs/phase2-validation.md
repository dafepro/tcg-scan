# Phase 2 controlled browser validation

These tests exercise the real application with fixed synthetic video made from public card scans. They establish outcomes on known development artwork. They do not establish physical-camera accuracy, held-out generalization, or production reliability.

## Fixed protocol

The app used its local Test video path, normal Live recognition/save rules, Quick auto-save, and the installed 19,665-reference collection. Recognition, prompts, OCR, saved-session counts and error messages came from the running app. Test fixtures supplied input pixels only. Inputs were fixed and hashed before the corresponding trials; packaging rechecked all sealed script/video files and all source-image hashes successfully.

- **Batch:** 40 seconds at 1080 × 1080, 20 fps. Blastoise, Rhydon, Articuno, Pikachu, then repeated Blastoise; eight seconds per pass. Distance and in-plane rotation change; each pass ends with about half a second of blank background. No explicit second-copy action. Expected count: four.
- **Heavy occlusion:** 60 seconds. Pikachu with synthetic distance, blur, translation, mild projective tilt, and a drawn thumb covering 37.1492929% of source-card area. The printed name remains visible; lower artwork/text and the identifier are covered. Thumb withdrawal is fixed at input 25–28 seconds.
- **Footer prompt:** 45 seconds. A smaller drawn thumb hides the lower-right identifier until 20 seconds, withdrawing by 23 seconds. The test input is held on an actual app prompt and explicitly resumed. The reveal is pre-authored, not generated by the app.

## Measurement limits

This is a tiny, known-art development replay using the same card-art groups that informed development. It is not a held-out dataset or a learned-model training result. Synthetic thumbs, tilt and blur do not reproduce sleeves, glare, holographic finishes, autofocus or physical hand motion. One cloud browser is not a representative phone-device sample.

Private screenshot and accessibility-tree logs preserve the observed app states, failures, timestamps and original-capture provenance. The final prompt OCR agreement uses reads 5 and 6, original captures `1:113` and `1:121`; the final heavy agreement uses reads 2 and 3, original captures `5:183` and `5:192`. Each agreeing pair has distinct source-pixel fingerprints. The first heavy read is retained and does not contain a literal 87/130 fraction. Screenshot sampling can affect scheduling and only brackets event times. The media clock, accessibility tree and screenshot are sampled sequentially, not atomically; the final-heavy catalog line appears in capture 01766’s screenshot before its exact text appears in the next DOM observation. Two OCR regions from one original image are not two independent captures. The private demo repeats actual captured stills, preserves observed playback intervals and labels gap cuts; it does not interpolate or reconstruct app output.

Before making broader claims, test unseen physical recordings on representative phones, with distractors, repeated identities and explicit copy actions, occlusion/glare, interruptions and independently scored ground truth. No deployment or CI success is implied by these local tests.
