# Learned recognition: evidence and remaining work

This branch adds a local XFeat 256/int 8 verifier and Fastweb corner proposals. It is still experimental. The learned physical-photo evidence below is Pokémon-only; Magic and Yu-Gi-Oh! have catalog/collection adapters but no equivalent validated learned gallery in this checkpoint. A matching score is not a probability, a reference name is not an exact physical printing, and a desktop replay is not a phone-camera accuracy test.

## Frozen model and matching protocol

Model revisions, byte lengths, SHA-256 values and licenses are recorded in [the model notice](../licenses/learned-models-NOTICE.md). The selected gallery contains 2,000 references and 804 distinct names. Queries retain up to 500 sparse 64-dimensional descriptors; references retain 256 spatially distributed int 8 descriptors with per-vector float 32 scales. A dual-hash index retrieves eight references, followed by exact per-reference mutual-nearest comparisons and unchanged spatial/artwork/RANSAC rejection gates. Every shortlisted rival must be checked before an automatic identity can be eligible.

The compact binary gallery is 39,755,008 bytes, including 842,496 bytes of manifest metadata. Descriptor records are loaded lazily from IndexedDB; the raw eight-record cache is 155,648 bytes and the decoded matching cache is 512 KiB. These are bounded payload sizes, not total browser RAM. No real-card gallery or source artwork is included in this repository.

## Accuracy evidence

The representation was selected on existing development photographs and fixed negative controls. An independent evaluator then ran a frozen configuration on five newly sourced physical photographs plus a card-back negative, saving all predictions before receiving labels. All 28 fully visible fronts were present in the gallery and their card identities were accepted correctly. The back and separately considered cropped backs were not accepted. This is a small in-gallery sample; it does not establish a broad open-set false-positive rate, all-game coverage, phone accuracy or reliable handling of every binder/sleeve/glare condition.

Exact printing remained unresolved: only one of 28 grouped front matches unanimously selected the correct catalog printing. The UI therefore saves identity-only entries, leaves physical condition and finish unknown, excludes them from valuation totals, and treats subsequent literal printing-field reads as separate evidence.

## Runtime equivalence

The browser adapter's feature extraction was compared on 107 controls/crops. Descriptors agreed closely with the frozen native implementation; two nonblank cases changed one selected keypoint among 500. A later full ORT-Web engine replay retained all 101 development-hypothesis decisions and all 84 fresh-photo-hypothesis decisions. These comparisons establish implementation agreement on those inputs, not new independent accuracy evidence.

An original bounded ONNX MatMul graph accelerates exhaustive descriptor multiplication. In Chromium, eight-reference matching took a median 12.7 ms versus 66 ms for scalar JavaScript, with about 2.5 ms additional transpose time. All 563 regression queries and 4,368 candidate comparisons preserved mutual-nearest pair indices; downstream frozen decisions were unchanged. Matrix scores remain float 32 similarity values.

End-to-end scene processing remains much slower than that isolated multiplication stage. Large development binder scenes improved from about 4.8 seconds to 3.6 seconds in the measured full-scene pipeline. A subsequent built-app still-photo binder replay saved its first identity after 4.43 seconds and all nine after 23.37 seconds. Pause, undo, resume, explicit new page, stop and reload retained exactly the intended 17 events across that test. Those figures include the current conservative three-observation scheduler; they are cloud desktop replay measurements, not phone-camera performance.

**An earlier capture implementation failed continuous-session stability.** An isolated longer hold was killed after about 59 seconds, with the operating system's OOM counter increasing. Main-page JavaScript heap remained small; renderer PSS was approximately 615–736 MiB in the observed interval. This establishes memory pressure but does not, by itself, identify a model leak. A separate control using video alone stayed small, while adding only canvas pixel readback and transfer to a native empty Worker reproduced large memory growth and an OOM kill without the application or models. Disabling tracing and explicitly detaching received pixel buffers did not remove that growth.

In a narrower control, `VideoFrame.copyTo` directly from the video into one round-tripped RGBA buffer processed 376 frames over 60 seconds with maximum-process PSS about 67 MiB. Routing the same capture through a resized canvas instead reached about 540 MiB, even when resetting the canvas backing every frame. These are transport controls, not full application stability results. The new preferred capture path therefore uses direct video, explicit `VideoFrame.close`, and a recycled input buffer. Camera constraints request bounded resolution, and actual dimensions are checked rather than assuming constraints were obeyed. Unsupported WebCodecs gets a clearly labeled one-frame-per-second compatibility path with a hard cumulative source-plus-readback budget and frame limit, then stops. The corrected direct-video pooled strict-mode build subsequently passed a six-minute genuine file-backed camera replay with all nine durable saves, all nine success overlays, Stop/reload persistence, and no crash or OOM-counter increase. Warm renderer PSS over minutes 1–6 was 335–399 MiB (median 365 MiB), startup peak 449 MiB, and after Stop 171 MiB. The same frozen build passed 42 browser cases with two intentional duplicate-mobile integration skips, all 28 physical-photo identity checks and the card-back negative. This is one cloud desktop environment, not phone certification. The later Quick-mode sampler and current-view protocol were checked separately, as recorded below.

## Continuous Quick-mode evidence

The later Quick candidate uses one unchanged strong learned identity match plus independently sampled, current-ROI continuity. It does not reuse cached identity as a new observation. Native video callback/frame time, bounded sample history, motion tracking and a final source-freshness check must all pass before a durable save. Geometry-cache and grayscale sampling were changed to fixed area averaging plus a standard 3×3 binomial filter; identity, rival, geometric and continuity rejection thresholds were not relaxed.

On an independent cloud-browser run with the same 2,000-reference gallery, a wider-framed static nine-card photo replay saved all nine by 10.4 seconds. Brightness variation reached nine by 10.9 seconds; ±2-pixel translation reached nine by 14.9 seconds while still moving. Combined translation and brightness saved seven during motion, then all nine by 23.8 seconds after the source settled at 15.5 seconds. These are labelled photo-derived replays, not measurements from a handheld phone. The original near-edge scene separately rejected a card whose corner was inside the required tracking margin; the UI asks for wider framing rather than claiming the card moved.

A default-stream replay saved the first card at 3.65 seconds from cold start and a different card 5.20 seconds after the warm scene-change command. Returning an already counted identity did not increment its count. Next copy explicitly rearmed only the visible verified identity, retained other identity latches, and reload preserved the intended three entries. Unverified proposals cannot revive an old stream success overlay. This explicit action remains necessary for an additional indistinguishable copy; detector absence is not accepted as proof that a physical card exited.

Three canonical fronts with identities verified absent from this specific gallery produced no eligible matches or saves. Removing the card during inference and freezing the native source produced no stale saves. A same-position scene swap saved the new identities without saving old ones. Canonical controls are not an independent physical open-set accuracy dataset; their coverage must be checked again for any expanded pack.

The final Quick camera candidate also passed a 363.535-second genuine file-backed camera hold with exactly nine durable saves, all nine success labels, correct Stop/reload persistence, no crash or safety stop, and no operating-system OOM-counter increase. In that separate soak, the first save was observed by 5.102 seconds and all nine by 15.218 seconds. Warm main-renderer PSS ranged from 338.41 to 444.01 MiB (median 380.35 MiB), with a fitted +2.17 MiB/min slope over this limited six-minute window; after Stop it fell to 173.16 MiB. Owned-browser PSS peaked at 728.62 MiB. This does not prove the absence of a longer-running leak. This is evidence for one cloud Chromium build and gallery. Whole-index behavior, the final distribution integration, phone hardware, and UI/UX review remain separate gates.

## Expanded-gallery browser verification

The completed private English paper-Pokémon pack contains **19,665 references / 4,416 names** in 155 files, totaling **391,001,940 bytes**. Its manifest SHA-256 is `82efef2f91f2d2338c4634a0284912679f994c835b3eef5d3632bcb9c10f5d19`. The reviewer independently verified every manifest/shard size and hash before testing the unchanged polished application.

A clean browser import took 8.405 seconds, and installed coverage was visible 122 ms after reload. The main page reported 14.1 MB used JavaScript heap plus 21.1 MB backing storage after import; those figures exclude the separate worker and native renderer allocations and are **not total browser RAM**. All 28 expected identities across the same five physical front photographs remained accepted with the expanded gallery, while the card-back photo remained ineligible. Individual whole-photo operations took 4.42–6.45 seconds. These are regression checks on the existing physical-photo sample, not a new independent held-out accuracy estimate.

A genuine photo-derived binder camera replay saved all nine correct identities by 12.546 seconds (observed with five-second polling), held exactly nine through 123.717 seconds, and preserved them after Stop/reload. Sampled main-renderer PSS peaked transiently at 612.51 MiB, stayed at or below 481.07 MiB after the first 30 seconds, and fell to 186.94 MiB after Stop; the OS OOM counter did not increase. A separate full-gallery stream replay observed its first cold save at 4.585 seconds and a warm different-card handoff at 5.276 seconds. Returning an identity did not recount it; scoped Next copy and reload retained the intended counts. This expands the gallery exercised by the earlier six-minute transport soak; it is not a six-minute full-gallery test or a phone measurement.

Three Pocket fronts were selected before inference by fixed positions among names/identity keys absent from the completed paper-card gallery. With distinct SHA-addressed source URLs, independently checked request bytes and inspected screenshots, Exeggutor ex, Elemental Switch and Cresselia ex produced zero eligible identities or saves over 12 seconds each. Three formerly absent 2,000-gallery controls—Battle City, Grusha and Aerodactyl Spirit Link—were present in the expanded pack and each saved the correct identity in approximately 3.9 seconds. These provider-canonical controls are not photographs of unknown physical paper cards and do not establish a general open-set false-positive rate. An earlier reused-image-URL sequence was excluded after pixel inspection showed a stale decoded input; it is not recognition evidence.

The polished build separately passed 44 browser cases, with two intentional duplicate mobile-integration skips, and four independent UI/UX checks across 320–1440-pixel viewports. Those viewport checks do not establish phone-camera performance. Exact printing, physical condition/finish, broader physical accuracy and unattended long-session counts remain unverified.

## Printing refinement

The optional local reader requires two distinct native-detail camera captures and a complete, explicitly scoped provider candidate list. It does not repair ambiguous OCR glyphs into a desired identifier. Live metadata checks returned 145 Pikachu candidates from TCGdex, nine Dwarven Demolition Team printings from Scryfall, and 59 Dark Magician set entries from YGOPRODeck. These counts are observations from 2026-10-12, not permanent catalog sizes. Provider records can omit physical editions/languages/finishes; completeness within a provider scope is not universal completeness.

Printed identifiers, unknown fields and retrieval source are stored separately. No OCR text, image crop or camera frame is included in a collection backup. Automated printing reads never make an entry eligible for a physical-card valuation by themselves.

An initial real browser printing probe saved the visual identity but never started OCR despite sufficient native detail. Its crop scheduler used previous-frame visibility and could miss the next fresh eligible match. The corrected scheduler requests pending saved identities while still requiring a current, strongly verified detection before cropping. The corrected path subsequently completed all six bounded reads with genuine bundled Tesseract on the same physical-photo-derived stream. OCR returned attack/copyright text but did not recover its tiny `10/102` footer. The finite provider candidate list in this test was an explicitly labeled fixture; it was not a live-catalog completeness test. The card remained identity-only with unknown finish/condition and no value. Stop terminated both OCR and vision workers. Thus scheduling, actual OCR delivery and cleanup passed, while successful automatic printing resolution on that photo did not.

That combined vision/OCR run peaked at approximately 641 MiB main-renderer PSS and fell to approximately 202 MiB after Stop. Initial retests had suffered OS memory-pressure kills while unrelated completed local experiments occupied roughly 4.7 GiB of RAM-backed temporary storage. Those artifacts were preserved with verified hashes on disk-backed storage; shared-memory use fell by approximately 2.5 GiB. The unchanged printing build then completed without an OOM-counter increase. These observations do not establish a phone-memory budget or a longer OCR-session stability guarantee.

## Release gates

- Isolated, sufficiently long actual-browser loops with bounded memory and no unexplained renderer failures
- Continuous single-card and binder saves with explicit first/all-save latency, backpressure and lifecycle tests
- Explicit counting semantics and source-current safety: unknown cards and constant-presence corner proposals must not be treated as proof of an empty scene; automatic identical-copy exit/reentry remains unsupported
- Whole-index retrieval and real-photo tests before claiming whole-game accuracy
- Independent desktop/mobile UI and accessibility review, followed by an honestly labeled cloud usage video
- Device testing before phone-specific performance claims

Raw evaluation photographs remain private local test inputs because redistribution permission was not established. Synthetic repository fixtures are original project assets and are labeled as mechanics tests.
